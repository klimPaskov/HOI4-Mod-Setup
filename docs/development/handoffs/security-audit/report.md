### High

#### HMS-SEC-001 - Apply trusts a renderer-supplied plan and independent root

Classification/reachability: confirmed defect in the registered `apply_installation` command.

Impact: the renderer receives a serialized plan, can submit that plan or a modified replacement with a separately supplied project root, and the Rust command marks the submitted object reviewed. Apply does not bind the request to a core-owned plan ID/session, approved canonical root, manifest hash, resolved source request, selected components, operations, generated artifacts, Git setup/approvals, conflict decisions, or prior local-file evidence. It re-downloads or accepts generated bytes based on caller-supplied plan fields and checks the result only against another hash in that same caller-supplied plan. A modified renderer invocation can therefore bypass the core review and source-selection boundary and reach the transaction runner with unreviewed file and Git plan state. Source downloads remain confined to the fixed repository client and syntactically full revisions; transaction/Git behavior was out of scope, so this finding does not assert an out-of-root write, network action, or push.

Current evidence:

- `src-tauri/src/commands.rs:25-35` registers `apply_installation` as a Tauri command.
- `src-tauri/src/commands.rs:261-285` derives initial Git setup from renderer state; `src-tauri/src/commands.rs:524-562` serializes that setup and approval fields into the returned plan.
- `src-tauri/src/commands.rs:566-570` returns only the serialized plan and discards the prepared bytes built by the core.
- `src-tauri/src/commands.rs:573-583` accepts a caller-supplied plan and independent root, sets only `dry_run_reviewed = true`, and checks the root only with `is_dir()`.
- `src-tauri/src/commands.rs:585-614` trusts caller-supplied operations, generated artifacts, source paths, and `plan.source.resolved_revision`.
- `src-tauri/src/commands.rs:615-627` compares fetched/generated bytes only with the caller-supplied operation hash.
- `src-tauri/src/commands.rs:629-630` passes the caller-supplied root and complete plan, including Git setup/approvals, to `run_transaction`.

Test evidence: `commands.rs` has no inline test module. The source tests at `src-tauri/src/source.rs:848-972` do not tamper with a plan, change the project root, mutate source/manifest/component/operation fields, alter generated artifacts, or omit approval.

Remediation:

- Retain the reviewed plan and prepared evidence in the Rust core under an opaque, single-use plan/session ID.
- Bind the canonical approved root, project identity, exact commit object, manifest hash, selected components, operations, artifacts, conflict decisions, local hashes, and explicit approval transition.
- On apply, load the core-owned plan, revalidate root and local state, and reject any client attempt to supply authoritative plan contents.
- If plans must survive restart, persist a non-secret integrity-protected record and verify it before use.

Regression tests:

- Mutate each bound field, including Git setup and Git/remote/push approvals, between review and apply and assert rejection.
- Supply a different root, symlinked root, stale local hash, altered generated content, extra operation, changed source path, changed destination, changed action, or false approval and assert that `run_transaction` is not called.
- Prove an unrecognized, reused, expired, or already-applied plan ID is rejected.

### Medium

#### HMS-SEC-002 - Destination identity and external Windows naming policy are incomplete

Classification/reachability: confirmed planner validation gap; downstream transaction collision handling was out of scope.

Impact: the current snapshot now applies its ASCII-lowercase key after tree expansion, resolving the prior exact-string ASCII collision gap. It still lacks Unicode normalization/full case identity and the selected macOS volume's case mode, so canonically equivalent or non-ASCII case-equivalent names can remain ambiguous. In addition, the explicit external-destination validator bypasses `normalize_relative_path` and does not reject a Windows alternate-data-stream suffix, reserved final component, trailing-dot/space normalization, or case collision. Ambiguous destination identity can undermine review, backup, apply, and rollback ordering.

Current evidence:

- `src-tauri/src/security.rs:95-97` defines destination identity with `to_ascii_lowercase()` only.
- `src-tauri/src/security.rs:213-223` provides a destination-set check using that same limited identity.
- `src-tauri/src/security.rs:226-247` applies the limited key only to component-root destinations.
- `src-tauri/src/source.rs:733-740` now applies `canonical_relative_key` to expanded destinations, but that key retains the ASCII-only/Unicode limitations.
- `src-tauri/src/security.rs:135-192` accepts an absolute external file path without applying the relative-path ADS/reserved-name/trailing-dot-space checks or a destination collision key.
- `src-tauri/src/security.rs:375-380` uses lossy OS-path conversion instead of rejecting an unrepresentable relative name.
- `src-tauri/src/security.rs:62-92` covers the common Windows device names, but there is no evidence or test for additional supported-Windows reserved-device spellings.

Test evidence: `src-tauri/src/security.rs:408-432` tests basic traversal and generated ASCII segments only. `src-tauri/src/source.rs:923-928` tests a glob example only. There are no Unicode NFC/NFD, non-ASCII case, invalid-encoding, external Windows device/ADS, or macOS volume-mode tests.

Remediation:

- Define one destination-identity policy for both root-contained and external destinations, apply it after complete tree expansion, and apply it again at the operation boundary.
- Normalize Unicode under an explicit cross-platform policy, reject lossy/unrepresentable names, and apply Windows plus actual target-volume case semantics.
- Conservatively reject portable components that would collide on either supported platform unless the product contract explicitly scopes them to one platform.
- Apply and test the complete Windows ADS, trailing-dot/space, and reserved-name policy—including alternate supported device spellings—to external destinations as well as project-relative paths.

Regression tests: ASCII and non-ASCII case pairs, NFC/NFD equivalents, nested tree expansions, internal and external Windows reserved names/ADS/trailing-dot-space interactions, invalid OS strings, and case-sensitive and case-insensitive macOS volumes.

#### HMS-SEC-003 - Path helpers do not close operation-boundary link/reparse races

Classification/reachability: confirmed defense gap at exposed plan/apply boundaries. A complete write exploit is not asserted because transaction code was out of scope.

Impact: containment checks canonicalize a parent once and return an ordinary path. A project directory can be replaced with a macOS symlink or Windows symlink/junction/reparse point after validation and before create/rename. `atomic_write` uses path-based creation and rename without a root capability or final-parent identity check. The project-root helper canonicalizes before looking for link components and is not called by plan/apply commands. These helpers therefore do not establish the accepted operation-boundary race defense.

Current evidence:

- `src-tauri/src/security.rs:99-128` performs one nearest-existing-parent containment check and returns a path for later use.
- `src-tauri/src/security.rs:135-192` performs path-based external link checks once and checks only `is_symlink()`, not a stable parent/file identity or explicit reparse-tag policy.
- `src-tauri/src/security.rs:196-210` checks existing components only for `file_type().is_symlink()` and has no explicit Windows reparse-tag policy.
- `src-tauri/src/security.rs:271-294` creates directories/files and renames by path without a root handle or parent identity revalidation.
- `src-tauri/src/paths.rs:72-86` canonicalizes the root before checking its canonical components, which cannot reveal links traversed in the originally selected spelling.
- `src-tauri/src/commands.rs:115-137` accepts a build-plan root using only `is_dir()`.
- `src-tauri/src/commands.rs:578-583` accepts an apply root using only `is_dir()`.
- `src-tauri/src/commands.rs:9` imports no `validate_project_root` or link-component enforcement.

Test evidence: no inline test covers `safe_join`, `validate_external_destination`, `reject_link_components`, `atomic_write`, `path_has_link_component`, or `validate_project_root`. There is no Windows junction/reparse swap or macOS symlink swap test.

Remediation:

- Convert an approved canonical root into a platform-specific root capability and use handle-relative/no-follow operations where supported.
- Revalidate final-parent and destination identity immediately around every create, backup, replace, rename, delete, and rollback step; fail closed on identity changes.
- On Windows, inspect and policy-check reparse attributes/tags, including junctions and mount points. On macOS, use no-follow/open-at style operations and verify ancestry by stable file identity.
- Make build/apply commands use the same root validator and bind that validated root as required by HMS-SEC-001.

Regression tests: race every mutation boundary by swapping an ordinary directory for a Windows symlink/junction/reparse point or macOS symlink, and prove that no project, backup, staging, external, or rollback operation escapes its approved root.

#### HMS-SEC-004 - Reachable opener and process policy lack exact identity and containment

Classification/reachability: confirmed reachable executable-resolution defect in `open_in_codex`, plus latent confirmed defects in the reusable `ProcessSpec` runner.

Impact: the registered `open_in_codex` command searches the inherited `PATH` for the first regular file named `codex`, `codex.exe`, or `codex.cmd` and spawns it directly; it does not establish an approved platform route or stable executable identity and validates the caller-supplied root only with `is_dir()`. Separately, the reusable runner allows basename equality, unrestricted `cwd`, and full inherited environment, while network, expected-write, and privilege behavior are not modeled. Its piped stdout/stderr are not drained while waiting, timeout kills only the direct child, and the configured output limit is applied after capture as a character count. The reachable opener permits path-precedence substitution, while the reusable runner can permit same-name substitution, inherited-secret disclosure, undisclosed writes/network/elevation, or unbounded completion behavior when wired.

Current evidence:

- `src-tauri/src/commands.rs:25-35` registers `open_in_codex`.
- `src-tauri/src/commands.rs:635-660` accepts a root with only `is_dir()`, selects the first same-named `PATH` file, and calls `std::process::Command` directly instead of the policy runner/platform adapter.
- `src-tauri/src/process.rs:10-22` has no approved working-root, network, expected-write, privilege, or process-tree policy.
- `src-tauri/src/process.rs:51-59` invokes the executable allowlist check.
- `src-tauri/src/process.rs:149-158` treats basename equality as executable identity.
- `src-tauri/src/process.rs:95-106` accepts arbitrary `cwd`, does not clear the inherited environment, and adds scoped secret values.
- `src-tauri/src/process.rs:95-100` pipes both outputs while `src-tauri/src/process.rs:112-128` polls without concurrent draining and kills only the direct child.
- `src-tauri/src/process.rs:126-139` collects before truncating and applies a character count to a byte-named limit.

Test evidence: `commands.rs` has no inline test module. `src-tauri/src/process.rs:171-205` tests a names-only preview and rejection with an empty allowlist. It does not cover opener `PATH` precedence, exact Codex identity, `.cmd` resolution, canonical project-root binding, same-basename substitution, cwd containment, inherited environment removal, concurrent dual-pipe draining, streaming byte bounds, descendant termination, or declared network/write/privilege behavior.

Remediation:

- Route `open_in_codex` through the platform adapter and the same policy boundary as other processes; bind a supported Codex executable/app identity, canonical reviewed root, approved argv form, and user-visible preview.
- Resolve all allowlisted executables through a platform adapter and bind a stable canonical file identity, approved argv forms, working roots, network/write disclosure, and no-elevation policy.
- Start from a minimal explicit environment and inject only credential names authorized for that exact executable/action.
- Drain stdout/stderr concurrently through a byte-bounded redactor.
- Enforce timeout, cancellation, and output limits on the complete child process tree/job/group and wait only within a hard terminal bound.

Regression tests: attacker-controlled earlier-`PATH` Codex names, unsupported `.cmd` routes, Windows `.exe` and macOS app-bundle identity, canonical/symlinked project roots, same-name tool binaries, outside-root cwd, parent-secret non-inheritance, secret output on both pipes, simultaneous large output, descendant-held pipes, descendant timeout, and network/write/elevation declaration checks.

#### HMS-SEC-005 - Redirect identity and response-size limits are not fail-closed

Classification/reachability: confirmed source-client hardening gap.

Impact: the client limits redirect count but does not explicitly restrict each redirect/final scheme and host or preserve final-source identity. It buffers the complete body before applying the 64 MiB check, so the stated bound is not a memory bound. The separate 512 MiB file check cannot be reached for bodies over the shared 64 MiB post-buffer limit. Unexpected redirects cannot be audited from the plan, and an oversized or slow response can consume resources before rejection.

Current evidence:

- `src-tauri/src/source.rs:68-75` configures only `Policy::limited(3)`.
- `src-tauri/src/source.rs:84-103` does not inspect the final URL, buffers `.bytes()` completely, and checks size afterward.
- `src-tauri/src/source.rs:239-290` routes manifest/tree requests through that behavior.
- `src-tauri/src/source.rs:291-304` routes selected files through the shared behavior and then advertises a later 512 MiB limit.

Test evidence: the inline tests at `src-tauri/src/source.rs:848-972` use no HTTP fake and cover no redirect, final URL, `Content-Length`, chunked-body, streaming-size, slow-body, or timeout behavior.

Remediation:

- Use an explicit redirect policy that permits only HTTPS and approved hosts, validates every hop, and records the final URL/identity.
- Stream response bodies through endpoint-specific byte limits; reject impossible/oversized declared lengths before allocation while enforcing the same bound on chunked bodies.
- Set documented, internally consistent limits for repository metadata, manifests, trees, and selected files.

Regression tests: approved redirect, cross-host redirect, HTTPS-to-HTTP downgrade, loop/count exhaustion, contradictory or oversized length, chunked over-limit body, slow body, and final-identity evidence.

#### HMS-SEC-006 - Commit-object and cross-platform command-route evidence remain incomplete

Classification/reachability: confirmed source-contract gap. Repository owner/name and fetch hosts are fixed; no cross-repository substitution was established.

Impact: current fetch methods reject revision text that is not a full 40-hex value, pinned releases boundedly dereference typed annotated tags, duplicate evidence paths are rejected, and selection now fails if a non-generated file lacks hash/size evidence. Those stale prior findings are resolved. However, a pinned/apply revision is still accepted on syntax alone rather than being proven as a commit object in the approved repository, and a release reference missing its object type defaults to `"commit"` instead of failing closed. Separately, the manifest's command-bearing `platforms: all` validation branch is a no-op while platform resolution treats `all` as supported; the code does not prove verified Windows and macOS command variants before reporting support. This violates the accepted exact-commit and verified-platform-route contracts.

Current evidence:

- `src-tauri/src/source.rs:160-165` accepts pinned commit mode after local shape validation only.
- `src-tauri/src/source.rs:167-235` performs bounded release-tag type dereferencing, but `src-tauri/src/source.rs:196-200` defaults a missing reference object type to `"commit"`.
- `src-tauri/src/source.rs:239-301` calls `validate_commit` before manifest/tree/file fetches.
- `src-tauri/src/source.rs:491-499` defines `validate_commit` as only length and ASCII-hex validation.
- `src-tauri/src/source.rs:398-420` now rejects duplicate listed evidence and missing listed hash/size, while `src-tauri/src/source.rs:742-754` rejects a selected non-generated file without matching evidence.
- `src-tauri/src/source.rs:431-441` contains a command-bearing `platforms: all` conditional with no enforcing action.
- `src-tauri/src/source.rs:611-626` reports support solely from the broad platform declaration.

Test evidence: `src-tauri/src/source.rs:889-928` covers checked-in manifest parsing, dependency behavior, empty evidence, and a glob example. There is no pinned-commit object-type test, missing release object-type test, blob/tree rejection, command-bearing `platforms: all` rejection, or per-platform verified-command-route test.

Remediation:

- Resolve and verify every pinned/apply revision as a commit object in the fixed approved repository, then bind that proof to the reviewed plan.
- Fail closed when Git object type is absent or unknown; retain the bounded annotated-tag dereference and reject non-commit terminals.
- Reject command-bearing `platforms: all` declarations unless schema and validation prove reviewed command variants for both supported platforms; otherwise require explicit per-platform routes and report unsupported honestly.

Regression tests: commit, tree, blob, annotated/nested tag, missing/unknown object type, excessive tag depth, Windows-only command declared as `all`, verified dual-platform command variants, and honest optional/required unsupported states.
