# 0.6.3 release validation

This patch release fixes the app-owned Meshy MCP launcher. Its release pull
request, subsequent main checks, and annotated `v0.6.3` tag workflow are
authoritative for their exact revisions and final publication. This record
does not claim signing, native-package, or publication results before those
gates finish.

## Defect

With app 0.6.2 and the reviewed Meshy 0.6.2 runtime installed (tree check
passing, 3,952 files), every `hoi4-mod-setup.exe --run-verified-meshy-mcp`
start exited with `ERR_MODULE_NOT_FOUND` for `dotenv`. The launcher hashes the
installed runtime's hoisted `node_modules` directory, then copied its contents
into a private directory named `package`. Node resolves bare specifiers only
from directories named `node_modules`, so the entry package could not see its
sibling dependencies. Meshy 0.4.0 had no such runtime imports; 0.6.2 imports
`dotenv`, `axios`, `express`, `zod`, and the MCP SDK.

## Change

The shared materializer now takes an explicit private layout. The Meshy route
uses `node_modules`; the HOI4 Agent Tools route keeps `package`, because its
npm-installed package nests its own dependencies and resolves inside its tree.
Relative paths, and therefore the reviewed tree SHA-256 and file count, are
unchanged. The package identity check, pre-spawn rehash, private Node copy
beside the tree, `OpenJS Foundation` publisher verification, Node hash at
spawn, cleared environment, and process ownership are unchanged.

Meshy 0.6.2 runs `dotenv.config()`, which loads `.env` from the child's
working directory: the coding client's project folder, which the route keeps
because downloads default to `<cwd>/meshy_output`. `dotenv` never overrides an
existing variable. An inventory of every environment read in the reviewed
runtime found four values that project content could abuse after `dotenv`
runs: `TRANSPORT` (HTTP listener), the `proxy-from-env` proxy settings that
axios consults for each authenticated request, `NODE_TLS_REJECT_UNAUTHORIZED`,
and `MESHY_API_HOST`. Module hoisting already reads `MESHY_API_HOST` before
`dotenv` runs, so it is pinned only as a defensive measure. The launcher now
sets `TRANSPORT=stdio`, `MESHY_API_HOST=https://api.meshy.ai`, `NO_PROXY=*`,
and `NODE_TLS_REJECT_UNAUTHORIZED=1` in the cleared child environment. These
are fixed non-secret values; the credential name and pins are validated
before spawn. Before 0.6.3 this path was unreachable, because the server did
not start.

The release also carries the updater dependency fix from commit `3c349a4`:
`tauri-plugin-updater` is built with `rustls-tls` only, so its optional zip
extraction path and the `zip` 4.6.1 crate (RUSTSEC-2026-0367, -0368, -0369)
are no longer compiled. Without it, the release workflow's `cargo audit` gate
fails on the current advisory database.

## Local evidence

All local checks ran in a separate worktree on Windows, using synthetic
fixtures and the real PATH Node. No real Meshy credential, user project, or
Meshy tool call was used.

- Regression: a synthetic hoisted tree whose ES module entry imports a sibling
  package by bare specifier runs under real Node after materialization; the
  Meshy route's own materialization does the same through its reviewed entry
  path. Restoring the prior `package` layout makes that Meshy test fail, and a
  separate test asserts the `package` layout's `ERR_MODULE_NOT_FOUND`.
- Negative: a package injected into, or a dependency replaced inside, the
  private `node_modules` is rejected before spawn; a different tree hash, file
  count, extra installed file, or Meshy package version is rejected.
- Environment: under real Node, a project `.env` loaded with dotenv's
  non-override rule cannot replace any pinned value or the credential,
  including lowercase names on Windows, while an unpinned entry is loaded.
  Pins that name the credential, are empty, contain NUL, or have an invalid
  name are refused, as is a Node hash mismatch.
- Launcher probe: a locally built debug launcher ran the real installed,
  reviewed Meshy 0.6.2 runtime with a dummy non-credential key and answered
  `initialize` (`@meshy-ai/meshy-mcp-server` 0.6.2) and `tools/list`
  (24 tools); no tool was called. From a scratch project whose `.env` set
  `TRANSPORT=http`, a proxy, an empty `NO_PROXY`, TLS rejection off, and a
  local API host, the real `dotenv` injected only the three unpinned entries,
  the server stayed on stdio, and nothing listened on the planted port.
  The unoptimized debug launcher needed several minutes before the server
  started; release-build start-up time was not measured.

## Release gates and limits

The release PR reruns the complete remote CI and security gates. Publication
uses the unchanged protected annotated-tag workflow and its native build,
signature, updater, and uploaded-byte verification.

A credential-bearing Meshy start, paid Meshy generation, and the existing
0.6.2 live-validation deferrals (updater replacement/restart/retry, OS-vault
round-trips, full native macOS wizard, real provider sign-in) are not covered
by this record. There is no schema, lock, migration, or credential-store
change.

The security skill and Meshy credential design were updated with the layout
and pinned-environment invariants.
